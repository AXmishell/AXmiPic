# Interfaces and Routes

The frontend is split into three interfaces by role, with a built-in setup mode:

| Path | Audience | Description |
|------|----------|-------------|
| `/` | All visitors | Public landing page: brand page + image upload (drag-and-drop/click/available to guests) + image plaza preview + login/user center entry |
| `/user/*` | Regular users | User center: my images, image processing, albums, image plaza, shares, tokens, plans, tickets, account settings |
| `/admin/*` | Administrators | Admin console: dashboard, user management, image plaza, site content, role policies, billing management, storage configuration, system settings, email logs |
| `/login` | Everyone | Regular user login / registration |
| `/admin/login` | Administrators | Separate administrator login page; once the secure entry is enabled it is only accessible with the entry cookie, otherwise 404 |
| `/admin/entry/<token>` | Administrators | Administrator secure entry; after validation it sets a 10-minute entry cookie and redirects to `/admin/login` |
| `/install` | Uninitialized instances | Setup mode (returns 404 once initialization is complete) |

After login, users are redirected by role: regular users go to `/user` and administrators to `/admin`; regular users visiting `/admin/*` are redirected to `/user`, and unauthenticated visitors to `/admin/*` are sent to the separate `/admin/login`. Administrators can enter the user center `/user` from the bottom of the console sidebar or the account menu in the top-right corner; while in the user center, the same location offers an "Admin Console" entry back to `/admin`.

### Admin secure entry

Can be enabled under "System Settings → Runtime Settings → Admin Secure Entry". When enabled:

- `/admin/login` cannot be accessed directly; the server returns 404;
- you must visit the secure entry generated by the admin console, `/admin/entry/<token>`;
- after successful validation, the entry sets an `axmipic_admin_entry` HttpOnly cookie valid for 10 minutes and redirects to the login page;
- the admin login API requires this entry cookie, which is cleared immediately after a successful login;
- logged-in administrator sessions remain valid and are unaffected by the secure entry toggle;
- invalid entry attempts on pages and the login API are all handled as 404.

The secure entry token never appears in the application access log (it is logged as `/admin/entry/[redacted]`), but reverse proxies/gateways should still redact the full URL themselves.

## Guest visitors

The system includes a built-in `Guest visitor` role group (smaller quota and upload size, with plaza, sharing, tokens, and other features disabled by default). When `auth.allow_guest_upload` is `true`, unauthenticated visitors can upload from the home page, subject to the Guest role group's rate limits and quotas.

To avoid all unknown visitors sharing a single quota pool and exhausting it quickly, guests use a **per-browser isolated** identity:

- On the first upload, the server creates a **separate Guest account** for the visitor and issues a signed cookie (`axmipic_guest`, HttpOnly); subsequent uploads from the same browser reuse that account, each enjoying its own `guest_quota_mb` quota.
- Changing the cookie yields a new account, so a **per-IP window quota** `auth.guest_ip_quota_mb` is also enforced (default window 24 hours, 0 means unlimited): once a client IP's total guest upload volume within the window exceeds this value, requests are rejected (HTTP 429). This prevents bypassing the per-guest quota by repeatedly changing cookies.
- Guest accounts do not appear in "User Management" and are not included in user counts; background jobs periodically clean up expired IP usage records and unused empty guest accounts.

> Note: the built-in legacy `guest` account is only used for compatibility and for policy resolution in anonymous read-only APIs; anonymous uploads no longer use it. To adjust the Guest group quota, go to "Operations → Role Policies", Guest visitor group; associated accounts' quotas sync automatically after the change.

## Setup mode

Setup mode is a standalone page that requires the user to **visit `/install` explicitly**. Frontend routing only checks the installation status for `/install`: when uninitialized it displays the setup wizard, and when initialized it returns 404; visiting `/` or other pages does not redirect automatically.

At startup, if `install.lock_file` (default `./data/install.lock`) does not exist, the instance is considered uninitialized and seeding of administrators and role groups is skipped. Completing the setup page will:

1. Validate and connect to the database, then run migrations;
2. Create the administrator account;
3. Seed the default role group and the `Guest visitor` role group;
4. Create the built-in `guest` account;
5. Write the configuration file and `install.lock`.

Once the lock file exists, initialization is considered complete and the setup entry closes: visiting `/install` again returns 404 instead of redirecting to the login page or admin console. Setup only creates administrator accounts (the `admins` table); afterwards you should go to `/admin` to log in. The regular `/login` validates against the `customers` table, so using an administrator account there reports an invalid username or password. To reinitialize, delete `install.lock` (and the database) and restart. Related APIs:

| Method | Path | Description |
|--------|------|-------------|
| GET | `/api/v1/install/status` | Setup status (no login required) |
| POST | `/api/v1/install` | Perform setup (no login required) |

Setting `install.disabled: true` completely skips the setup check (useful for testing and container orchestration).

> `POST /api/v1/install` does not require a setup token and only uses `install.lock_file` to determine whether initialization is complete. When deploying, make sure the setup page cannot be reached first by others on the public internet before you finish; you can also configure `auth.bootstrap_admin` to skip setup mode.

## Console interaction conventions

- **Global search**: press `⌘K` / `Ctrl+K` in the console to open page search, with arrow keys to select, Enter to navigate, and `Esc` to close; the top bar also provides an entry point. The search index shares its source with the sidebar navigation (`web/src/utils/navigation.ts`), keeping menus and search consistent.
- **Sidebar collapse**: on desktop the sidebar can be collapsed from the top bar (232px ↔ 56px), and the collapsed state is stored in `localStorage`; mobile still uses a drawer.
- **Content width**: the admin console content area is capped at 1600px, while the user center stays at 1200px, balancing data-dense pages and form readability.
- **Unsaved-changes protection**: the Runtime Settings tab of System Settings tracks dirty state per settings domain, provides a sticky "Save all / Discard changes" bar, and prompts when leaving the route or closing the page.
- **List pagination**: orders, tickets, reports, and notification logs use server-side pagination; configuration lists (plans, policies, storage, etc.) load in full because their size is bounded.
- **Changing username**: both administrators and users can change their own username on the account settings page, which requires the current password; when TOTP is enabled, a dynamic verification code is also required. Usernames preserve the case as entered for display, but login and uniqueness checks are case-insensitive; after a change the current session remains valid and the old username stops working immediately.
- **User management editing**: administrators can edit the username and email of regular users or administrators in user management, and optionally reset the password. Changing the email resets the verification status; resetting the password does not immediately invalidate the target user's existing sessions.
